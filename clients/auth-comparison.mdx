# RollingGo MCP Integration Overview

RollingGo MCP provides two distinct integration modes to address varying business requirements and project maturity levels:

- **API Key Quick Integration**: Authenticates via a straightforward Bearer Token and provides 3 core search tools. Designed for rapid prototyping, internal tooling, and functional testing with self-service onboarding in under 5 minutes.
- **OAuth 2.0 Full Integration**: Leverages the industry-standard Authorization Code flow and provides a comprehensive 7-tool transaction suite. Enables closed-loop, in-Agent payment processing and end-to-end order lifecycle management, engineered for enterprise production deployments.

Architectural selection should be evaluated across **project phase, payment requirements, user experience expectations, and engineering resources**.

---

# 1. MCP Protocol & RollingGo MCP Service Overview

## 1.1 What is MCP?

MCP (Model Context Protocol) is an open, standardized protocol designed to seamlessly connect AI models with external data sources, business tools, and operational systems.

Traditional AI system integrations commonly rely on point-to-point connections:

> N AI Applications × M Enterprise Systems = N × M Custom Integrations

MCP standardizes connections over **JSON-RPC 2.0**, reducing integration complexity from **N × M down to N + M**, delivering:

- Single integration effort
- Standardized RPC invocations
- Universal model interoperability
- Centralized access and permission governance
- Dynamic tool and capability discovery

## 1.2 What is RollingGo MCP?

RollingGo MCP is a **domain-specific service dedicated to hotel bookings and travel workflows**, built on top of the MCP protocol. It equips AI Agents and intelligent applications with standardized capabilities for:

- Hotel search and discovery
- Rich hotel detail queries
- Real-time rate and inventory confirmation
- Hotel room reservation
- In-session payment generation
- Order history lookup
- Detailed order lifecycle tracking

RollingGo MCP abstracts disparate, heterogeneous hotel supplier APIs into unified, ergonomic MCP Tools. Developers can rapidly construct fully capable hotel booking agents without wrestling with proprietary supplier protocols.

## 1.3 Technical Architecture

MCP utilizes a Client-Server two-tier architecture:

**MCP Server**

Encapsulates and governs:

- Hotel business domain logic
- Tools (execution interfaces)
- Resources (contextual data assets)
- Prompts (curated instructions)
- Permission and authorization controls
- Operational logging and security auditing

**MCP Client**

Embedded within the AI Agent or host application. Discovers and invokes tools exposed by the MCP Server through standardized MCP protocol messages.

This decoupled architecture isolates server capabilities from client runtimes. When tools, business policies, or upstream vendor APIs evolve, updates are deployed centrally on the Server without requiring modifications to client implementations.

# 3. API Key Quick Integration

## 3.1 Key Advantages

### Rapid Onboarding

Developers obtain an API Key instantly via the developer portal and can start invoking tools immediately by injecting an HTTP header.

Initial integration can be completed in **approximately 5 minutes**.

### Zero Implementation Barrier

Requires only an HTTP Authorization header:

```http
Authorization: Bearer YOUR_API_KEY
```

Eliminates the need to construct OAuth state machines, token exchange endpoints, or refresh schedulers.

### 100% Self-Service

Developers apply and configure credentials directly without waiting for commercial review or enterprise contracting.

### Ideal for Rapid Validation

Specifically tailored for:

- Minimum Viable Products (MVPs)
- Concept and functionality verification
- Internal employee utilities
- Early technical research
- Fast prototypes and hackathons

# 4. API Key Use Cases and Limitations

## 4.1 Applicable Scenarios

### Internal Utilities

Examples include:

- Enterprise travel inquiry dashboards
- Internal hotel search bots
- Market research and hotel data analysis tools

### Functional Prototyping

Used to quickly test and validate:

- Hotel search relevance
- Real-time availability across destinations
- Rich hotel metadata and amenity retrieval
- LLM search prompt quality

### Platforms with Existing Checkout Infrastructure

Established OTAs or travel agencies with proprietary booking and checkout engines can utilize RollingGo MCP purely as an auxiliary supply and catalog discovery feed.

---

## 4.2 Limitations

### Fragmented Payment Experience

Under API Key mode, when a user selects a room, they must be redirected out of the conversation to the RollingGo H5 page or Mini Program to complete payment:

> Agent Dialogue → Redirect to RollingGo H5 → Checkout & Payment

This handoff breaks conversational continuity and risks drop-off.

### Constrained Order Visibility

API Key mode does not provide:

- Historical order lookups
- Granular booking status queries
- In-app cancellation or post-booking assistance

Post-sales inquiries must be handled externally or through custom developer database tracking.

### Coarse-Grained Authorization

API Keys represent application-level identity. They cannot naturally scope permissions per individual end-user.

### Secret Management Responsibility

Developers must observe credential hygiene:

- Store API Keys strictly in server-side environment variables
- Never expose API Keys in client-side code or public repositories
- Configure IP whitelisting in production
- Enforce application-side rate limiting to prevent key misuse

# 5. OAuth 2.0 Full Integration

## 5.1 Core Architecture

OAuth 2.0 utilizes the standard **Authorization Code Flow (with PKCE support)**:

```text
End User
   ↓
Developer Agent / Host App
   ↓
RollingGo Authorization Server
   ↓
User Grants Permission
   ↓
Authorization Code Issued
   ↓
Client Exchanges Code for Access Token
   ↓
Agent Calls RollingGo MCP with User Token
```

The scoped Access Token accompanies all subsequent MCP Tool calls to identify and authorize operations on behalf of the specific user.

---

# 6. Security and Technical Advantages of OAuth 2.0

Compared to static credentials, OAuth 2.0 is purpose-built for enterprise-grade production reliability:

## 6.1 Short-Lived Access Tokens

Access tokens carry constrained expiration windows, substantially mitigating the impact of credential exposure.

## 6.2 Refresh Token Rotation

Enables automatic token renewal in the background without prompting users for repeated manual re-authorization.

## 6.3 Granular User-Level Access Controls

Permissions are scoped strictly to the authenticated user and authorized operational bounds, honoring the principle of least privilege.

## 6.4 Rich User Identity Context

Invocations are permanently anchored to verified user accounts, enabling:

- Personalized order retrieval
- Automated check-in and cancellation workflows
- Behavioral analytics and recommendation engines
- Complete audit logging
- Tailored loyalty and VIP tier recognition

# 7. Complete OAuth 2.0 Tool Suite

OAuth 2.0 provides 7 production-grade tools spanning the full travel booking lifecycle:

## 7.1 Search & Discovery

```text
getHotelSearchTags
searchHotels
getHotelDetail
```

Query hotel lists, apply multi-criteria filtering (location, amenities, ratings, budgets), and retrieve room category details.


Verifies real-time room availability, confirms final dynamic room rates, and locks inventory to eliminate booking discrepancies caused by stale prices.

## 7.3 Reservation & In-Agent Checkout

```text

```

Generates direct checkout links or QR payment prompts, enabling users to complete transactions directly within the conversation window.

## 7.4 Post-Booking Order Management

```text
searchHotelOrders
getHotelOrderDetail
```

Empowers the Agent to:

- Retrieve past and upcoming reservations
- Inspect detailed booking vouchers and confirmation numbers
- Track payment and fulfillment status in real time
- Coordinate cancellations, modifications, and customer service

# 8. Core Business Value of OAuth 2.0

## 8.1 Seamless In-Agent Experience: Zero Handoff

**API Key Flow**:

```text
Search → Room Selection → Redirect to RollingGo H5 → External Payment
```

**OAuth 2.0 Flow**:

```text
Search → Price Compare → In-Agent Booking → Instant Payment → Voucher Lookup
```

The entire transaction journey occurs seamlessly within the developer's own Agent or conversational interface.

Users never leave the chat canvas, resulting in higher conversion rates, superior user satisfaction, and reduced churn.

---

# 9. Data Ownership & Customer Retention

Under the OAuth 2.0 Authorization Code model, authenticated user relationships and contact identities (e.g., verified phone numbers) tie directly into the developer's platform ecosystem.

This empowers developers to build and retain:

- Proprietary user profiles
- Comprehensive transaction histories
- Re-engagement and repurchase loops
- Personalized AI recommendation engines
- Native loyalty and rewards programs
- Unified customer lifecycle management

Under API Key mode, transactions finalize on RollingGo H5, meaning order relationships and customer accounts are primarily anchored on the RollingGo side, relegating the developer to a traffic referral role.

---

# 10. Brand Consistency & White-Labeling

With OAuth 2.0, users remain immersed in the developer's branded application from initial query to final receipt.

Users are never redirected to third-party brand interfaces during payment or order lookup.

For businesses looking to:

- Build strong proprietary brand equity
- Deliver unified, bespoke user experiences
- Maintain complete commercial ownership
- Establish hotel booking as a core native feature

OAuth 2.0 represents the indispensable technical foundation.

# 16. Key Risk Factors & Mitigations

## API Key

Key Risks:

- User friction during external H5 payment redirection
- Inability to inspect or resolve user order issues directly
- Exposure risks of static API keys
- Absence of user-level access controls

Mitigation Checklist:

- Optimize H5 redirect and callback UX
- Store keys strictly in server environments (never client bundles)
- Enforce IP whitelisting on upstream gateways
- Monitor rate limits and anomaly spikes

## OAuth 2.0

Key Considerations:

- Initial architectural and implementation complexity
- Implementing robust OAuth 2.0 authorization code handshakes
- Secure token lifecycle management (storage, renewal, revocation)
- Standard corporate security, data privacy, and compliance reviews

# 17. Final Guiding Principles

The decision can be summarized in one core maxim:

> **Use API Key for rapid prototyping; use OAuth 2.0 for enterprise production applications.**

To break it down:

**API Key = Rapid Onboarding + Minimal Barrier + Immediate Validation**

The optimal choice for getting hotel booking capabilities running in minutes.

**OAuth 2.0 = Deep Integration + Customer Ownership + Closed-Loop Payments + Full Order Lifecycle**

The definitive architecture for building a sustainable, long-term enterprise hotel booking solution.

For evolving products, a phased rollout strategy is strongly recommended:

```text
Phase 1: API Key
Rapidly validate market appetite and AI agent capabilities
       ↓
Phase 2: Product Maturity
Define user journey, unit economics, and operational flows
       ↓
Phase 3: OAuth 2.0
Deploy full integration, in-Agent payments, and lifecycle management
```

In summary:

> **API Key is the lightweight gateway for rapid access and traffic referrals; OAuth 2.0 is the enterprise vehicle for deep integration, customer retention, and seamless in-Agent experiences.**

If your goal is simply to equip an Agent with hotel search capabilities, API Key delivers everything you need today. If your goal is to make hotel reservations a signature native capability of your product—allowing users to **search, compare, reserve, pay, and track orders entirely within the Agent conversation**—**OAuth 2.0 Authorization Code mode** is the clear path forward.
